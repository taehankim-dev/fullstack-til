# 07. 백엔드-하드웨어 연동: 커맨드 큐잉과 서킷 브레이커

## 0. 오늘 다룰 상황
- 백엔드가 특정 하드웨어(장비/디바이스)로 명령(신호)을 보내야 하는데, 그 하드웨어가 **다운됐거나 재기동 중**이라 응답이 없거나 연결이 끊긴 상태일 수 있음
- 지금까지 다룬 세션들은 "서버끼리" 이중화/가용성을 다뤘는데, 이번엔 **백엔드 ↔ 물리적 하드웨어** 사이의 신뢰성 문제라서 조금 다른 종류의 문제임

## 1. 문제 상황
- 하드웨어가 꺼져있는 상태에서 그냥 명령을 보내면:
  - 응답이 올 때까지 타임아웃 시간 내내 기다리게 됨 (커넥션/스레드가 오래 묶임)
  - 결국 실패하면 그 명령은 그냥 유실됨 — 사용자나 상위 시스템은 "명령이 실행됐는지 아닌지"조차 알 수 없음
- 매번 재시도하려고 매 요청마다 타임아웃을 끝까지 기다리는 것도 비효율적임 — 하드웨어가 아예 꺼져있는 걸 알면서도 매번 "기다렸다가 실패"를 반복하는 셈

## 2. 해결 원리

### (1) 디바이스 상태 머신 — 연결 상태를 추적
- 백엔드가 하드웨어의 상태를 `CONNECTED` / `DISCONNECTED` / `RECONNECTING` 중 하나로 계속 추적함
- 보통 하트비트(heartbeat, 주기적인 ping)로 "지금 살아있나?"를 확인. 몇 번 연속 실패하면 `DISCONNECTED`로 전환

### (2) 커맨드 큐 — 끊긴 동안은 쌓아두기
- 하드웨어가 `DISCONNECTED`일 때 들어온 명령은 바로 버리지 않고 **큐(FIFO)**에 쌓아둠
- 하드웨어가 다시 `CONNECTED`로 돌아오면, 큐에 쌓인 명령을 순서대로 꺼내서 재전송

### (3) 서킷 브레이커 — "이미 끊긴 걸 알면" 빨리 판단하기
- 하드웨어가 응답 없음을 감지하면, 그 다음부터 들어오는 명령들은 **매번 타임아웃을 기다리지 않고 즉시 큐로 보냄** (Circuit Open 상태)
- 대신 주기적으로 "지금 살아났나?" 테스트 신호를 하나만 보내보고(Half-Open), 성공하면 Circuit을 다시 닫고(Closed) 정상적으로 큐를 비우기 시작

## 3. 아키텍처 다이어그램

```
[App] --명령--> [Device Connection Manager]
                         |
                 지금 상태가 CONNECTED?
                    /            \
                  예              아니오 (Circuit Open)
                   |                   |
         하드웨어로 즉시 전송      [Command Queue] 에 쌓음 (FIFO)
                                        |
                        하트비트 복구 감지 (Half-Open → Closed)
                                        |
                                        v
                        큐에서 순서대로 꺼내 재전송
```

## 4. 짚고 갈 한계
- **순서 보장**: "문 열기" 다음 "문 닫기"처럼 순서가 중요한 명령이면, 큐는 반드시 FIFO를 지켜야 하고 재전송 중에 새 명령이 끼어들어도 순서가 꼬이지 않게 해야 함
- **영속성**: 큐를 메모리에만 두면 백엔드 서버 자체가 재시작될 때 큐 내용이 날아감. 명령이 중요하면(결제, 안전 관련 등) Redis나 DB에 큐를 영속화해야 함 (여기서 지난 Redis 세션들과 연결됨)
- **TTL(유효시간)**: 무한정 쌓아두면 안 됨. "5분 넘게 전달 못 하면 의미 없는 명령"이라면 TTL을 둬서 오래된 명령은 버리고 상위 시스템에 실패를 알려야 함
- **멱등성(idempotency)**: 재전송했는데 하드웨어가 중복으로 그 명령을 또 실행하면 위험한 경우(예: 모터가 두 번 작동)가 있을 수 있어서, 멱등성 처리가 필요할 수 있음
- 참고: MQTT 프로토콜(QoS 레벨, Last Will and Testament)이 바로 이런 "불안정한 디바이스와의 통신"을 표준화한 것 — 레포에 있는 `Theory/MQTT.md`와 연결됨

## 5. 아키텍처 설계 / 장애 시나리오 질문

**Q. 하드웨어가 끊긴 동안 "문 열기" 명령이 큐에 쌓였다고 하자. 그런데 그 사이에 사용자가 마음을 바꿔서 "문 열기 취소"에 해당하는 요청이 들어왔어.**
**이 상황을 지금의 큐 구조에서 어떻게 처리해야 할까?**

(힌트: 단순히 "취소" 명령도 큐 맨 뒤에 또 쌓는 게 맞을지, 아니면 다른 방식이 필요할지 생각해봐.)

- **답변**: 큐 뒤에 "취소" 명령을 쌓는 건 비효율적(문 열기 실행 후 문 닫기를 또 실행하는 것뿐이라 부하만 늘림). 큐에 쌓여있는 "문 열기" 명령을 직접 제거하는 게 맞고, 다른 명령들의 순서는 그대로 유지해야 함.
- **멘토 피드백**: 핵심 통찰 정확함 — "취소를 뒤에 쌓기"보다 "아직 안 보낸 명령을 큐에서 직접 제거"하는 게 훨씬 효율적이고, 실제로 BullMQ 같은 잡 큐 시스템도 "아직 실행 안 된 작업 취소(cancel pending job)"를 지원하는 이유가 이거임.
  - **추가로 고려할 타이밍 문제**: "문 열기 취소"가 도착한 순간, "문 열기" 명령이 어디 있는지에 따라 처리가 달라짐:
    1. 아직 큐 안에 있음 → 큐에서 바로 제거하면 끝
    2. 이미 큐에서 나가서 하드웨어로 전송 중이거나 이미 실행됨 → 큐에서 지울 게 없으므로, "취소"는 "닫기"라는 **별도의 새 명령**으로 다시 보내야 함
  - 완전한 처리 흐름: **"큐에서 찾아서 제거 시도 → 못 찾았으면(이미 나갔다는 뜻) 명시적 반대 명령을 새로 큐에 추가"**의 2단계 필요. 물리적 세계(문이 실제로 열림)는 메모리처럼 취소가 안 되기 때문에, 일반 서버-서버 통신보다 하드웨어 연동이 까다로운 이유가 여기에 있음.
  - (참고: 이 "큐에서 제거 시도"와 동시에 진행 중인 큐 flush(재전송 루프)가 겹치면 race condition이 생길 수 있음 — 더 깊은 주제라 오늘은 짚고만 넘어감)

## 6. 심화 - 큐 Flush와 취소의 Race Condition

### 문제 상황
큐를 비우는(flush) 백그라운드 루프가 이런 식으로 돌고 있다고 하자:

```typescript
while (true) {
  if (deviceStatus === "CONNECTED" && queue.length > 0) {
    const command = queue.shift();       // ① 큐에서 꺼냄
    await sendToHardware(command);       // ② 전송 (시간이 좀 걸림)
  }
}
```

"문 열기" 명령이 ①에서 막 `shift()`로 큐 밖으로 나온 바로 그 순간(아직 ②의 `sendToHardware`가 끝나기 전), 사용자의 "취소" 요청이 도착해서 "큐에서 문 열기를 찾아 제거"를 시도한다고 하자.

**문제**: 그 시점에 명령은 이미 큐 밖에 있음(꺼내졌지만 아직 하드웨어에 도착은 안 함). 취소 로직이 큐를 뒤져봐도 못 찾아서 "이미 나갔다"고 판단 → "닫기" 명령을 새로 큐에 넣음. 근데 타이밍에 따라 "열기"가 하드웨어에 도착하기도 전에 "닫기"가 먼저 도착해버리는 **순서 역전**이 생길 수 있음.

### 왜 이게 "race condition"인가
"큐에서 찾기(취소 로직)"와 "큐에서 꺼내기(flush 루프)"가 서로 독립적으로 큐라는 **공유 자원**을 건드리는 두 흐름이라서, 그 사이의 타이밍에 따라 결과가 달라짐. JS는 싱글 스레드지만, `await` 지점(`sendToHardware` 호출 중)에서 제어권이 다른 작업으로 넘어갈 수 있다는 걸 기억해야 함 — 지난 이벤트 루프 세션에서 본 "동기 코드 사이에 다른 작업이 끼어들 수 있는 지점"이 바로 여기.

### 해결 원리
- **단일 처리 루프로 직렬화(Serialization)**: "명령 전송"과 "취소 요청"을 서로 다른 코드 경로에서 각자 큐를 건드리게 하지 말고, **둘 다 같은 큐에 들어가는 이벤트**로 합쳐서 한 번에 하나씩만 순차 처리하게 만듦. 이렇게 하면 "동시에 둘 다 큐를 건드리는" 상황 자체가 원천적으로 안 생김 — 공유 자원에 접근하는 진입점을 하나로 좁히는 것.
- 즉 "취소"도 별도 함수 호출이 아니라, "큐에 들어가는 또 다른 종류의 이벤트" 하나로 다뤄야 함.

### 추가 질문: "꺼냈지만 전송 중"인 상태는 직렬화해도 사라지는 거 아니야?

**질문**: 큐에서 "문 열기"를 꺼냈지만 `sendToHardware`를 실행 중인 상태라면? 그런 경우는 존재하지 않는 거야?

- **답변**: 아니, 그 상태는 사라지지 않음. 직렬화가 그 구간 자체를 없애는 게 아니라, **그 구간이 진행되는 동안 다른 누구도(취소 핸들러 포함) 끼어들 수 없게 막는 것**임. 취소 요청이 그 순간 도착하면, 즉시 실행되는 게 아니라 같은 큐(처리 줄)에 줄을 서서 "문 열기" 전송이 완전히 끝날 때까지 기다림. 그래서 취소 핸들러의 코드가 실제로 실행되는 시점엔 항상 "큐에 있음" 또는 "이미 끝남" 둘 중 하나만 보임 — "전송 중"인 애매한 상태를 직접 관찰하는 일이 없음.
- **비유**: 프로그래밍의 **락(lock) / 크리티컬 섹션(critical section)**과 같은 개념. 락을 건다고 작업 시간이 0이 되는 게 아니라, 그 시간 동안 다른 작업이 같은 자원을 못 건드리게 줄 세우는 것. "전송 중" 구간이 바로 락이 걸린 구간이고, 취소 요청은 락이 풀릴 때까지 대기열에서 기다리는 것.

### 질문
"취소" 이벤트도 같은 큐에 들어가는 이벤트로 처리한다고 했을 때, 그 이벤트를 처리하는 핸들러가 순서대로 해야 할 일을 설명해볼래? (지난 질문에서 나온 2단계 처리와 연결해서 생각해봐.)

- **답변**: 잘 모르겠음
- **멘토 설명**: 핵심은 "모든 이벤트(일반 명령 + 취소 요청)가 하나의 큐에서, 앞 항목의 처리(꺼내기+전송까지)가 완전히 끝난 뒤에만 다음 항목으로 넘어간다"는 직렬화 규칙. 이게 보장되면 "취소" 핸들러가 실행될 때 가능한 경우는 딱 둘뿐임:
  1. **"문 열기"가 아직 큐에 남아있음** (자기 차례가 안 와서 못 꺼내진 상태) → 큐에서 찾아서 그냥 제거. 하드웨어에 아무것도 안 보내도 됨.
  2. **"문 열기"가 이미 처리를 마침** (꺼내져서 `sendToHardware`까지 완료) → 큐에서 못 찾음 → "닫기"라는 새 명령을 큐 끝에 추가해서 같은 직렬화 순서를 타고 나중에 전송.
  - **왜 race condition이 없어지는지**: 예전엔 "꺼내졌지만 아직 전송이 안 끝난" 애매한 제3의 상태가 있어서 문제였음(① `shift()` 직후, ② `await sendToHardware()`가 끝나기 전에 취소가 끼어듦). "한 항목을 완전히 끝내야 다음으로 넘어간다"는 직렬화 규칙이 있으면, 취소 핸들러의 차례가 왔다는 사실 자체가 "앞 항목은 이미 완전히 끝났다"를 보장해줌. 그래서 "큐에 있냐 없냐"라는 이분법만으로 충분해지고, 중간의 애매한 상태를 신경 쓸 필요가 없어짐.
