# 03. Redis 이중화 - Replication과 Sentinel

## 0. 지난 세션 복습
- Redis를 세션 저장소로 1대만 두면, 그 Redis가 죽는 순간 **전체 사용자가 동시에** 영향받는 전면 장애가 됨 (SPOF)
- 이번 세션은 "Redis를 어떻게 1대 장애에서도 살아남게 하느냐"

## 단어 설명
- Sentinel: Redis를 Master - Replica(Slave) 복제 구조로 운영할 때, Master 노드가 죽었을 때 이를 자동으로 감지하고 새로운 Master를 선출(Failover)해 주는 감시 및 오케스트레이션 시스템.
- Quorum: 사전적으로 '정족수(의결에 필요한 최소 인원수)'를 뜻하며, Redis Sentinel에서는 "Master가 다운되었다고 판단하기 위해 동의해야 하는 Sentinel의 최소 개수"를 의미

## 1. 문제 상황
- Redis는 기본적으로 데이터를 메모리에 둠. 프로세스가 죽으면 메모리 데이터도 같이 사라짐
- 디스크 백업(RDB 스냅샷, AOF 로그)을 켜면 **재시작 후 데이터는 복구**되지만, 복구되기 전까지는 **서비스가 멈춤**
- 즉 백업은 "데이터 소실"을 막을 뿐, "서비스 중단"은 못 막음. 그리고 재시작/복구는 보통 사람이 개입해야 함

→ 필요한 것: **데이터를 다른 서버에도 복제해두고(다운타임 줄이기), 죽었을 때 자동으로 다른 서버를 주인으로 세우는 것**

## 2. 해결 원리 (1단계): Replication (마스터-레플리카)
- **Master**: 쓰기(write)를 담당
- **Replica**: Master의 데이터를 복사해서 가지고 있음 (읽기 분산에도 쓸 수 있음)
- 복제는 기본적으로 **비동기(asynchronous)**: Master가 응답한 직후 Replica로 복사가 흘러감 → 그 짧은 틈의 데이터는 Master가 죽으면 유실될 수 있음

> 근데 아직 부족함: Master가 죽어도 **자동으로 Replica를 승격시키는 주체가 없음**. 누군가 손으로 승격시켜야 함.

## 3. 해결 원리 (2단계): Sentinel (자동 장애 전환)
- Sentinel은 Redis 옆에서 따로 떠 있는 **감시 프로세스**. 보통 **홀수 대(3대 이상)**로 띄움
- 역할:
  1. Master와 Replica를 계속 헬스체크
  2. Master가 죽었다고 **다수결(quorum)**로 합의하면, Replica 중 하나를 새 Master로 승격
  3. 나머지 Replica가 새 Master를 보도록 재설정
  4. 클라이언트는 "지금 Master가 누구냐"를 Sentinel에게 물어봄 → 주소가 바뀌어도 앱 코드는 그대로

- **왜 홀수 + 다수결인가?** 네트워크가 끊겨서 Sentinel이 둘로 갈라졌을 때, 소수 쪽이 멋대로 Master를 바꾸면 **Master가 2개 생기는 문제(split-brain)**가 생기기 때문

## 4. 아키텍처 다이어그램

```
           [App 서버들]
                |  "지금 Master 주소 줘"
                v
        [Sentinel 1] [Sentinel 2] [Sentinel 3]   ← 서로 감시 + 다수결
              |           |           |
              +-----------+-----------+
                          |  헬스체크
          쓰기 ↓                       ↓ 복제
     [Redis Master] ───복제───→ [Redis Replica 1]
                       └──────→ [Redis Replica 2]

Master 장애 시: Sentinel 다수결 → Replica 1을 Master로 승격 → Replica 2도 새 Master를 따라감
```

## 5. 짚고 갈 한계
- **비동기 복제** → 장애 전환 순간 아직 복제 안 된 최근 쓰기는 유실될 수 있음 (강한 일관성이 필요하면 `WAIT` 같은 옵션 검토 필요)
- Sentinel은 **가용성(자동 복구)**을 해결하지, **쓰기 분산(샤딩)**은 해결하지 않음. 데이터가 한 Master 용량을 넘어서면 Redis Cluster가 필요 (다음 주제 후보)

## 6. 아키텍처 설계 / 장애 시나리오 질문

**Q. Sentinel을 2대만 띄워두고 quorum을 2로 설정했다고 하자. 이때 Master가 죽고 Sentinel 한 대마저 같이 죽었다면, 자동 장애 전환이 일어날 수 있을까? 이유와 함께 생각해봐.**

(힌트: 3대일 때 quorum 2가 왜 의미가 있었는지 생각해보면 답이 보여.)

- **답변**: 자동 장애 전환이 일어날 수 있다. 다수결이니까, 살아있는 Sentinel 한 대의 결정으로 이뤄질 수 있다.
- **멘토 피드백**: 결론이 반대야. 다수결 기준은 "살아있는 쪽 수"가 아니라 **"전체 Sentinel 중 quorum 이상이 동의했는가"**. 2대 구성에서 quorum 2를 채우려면 2대 모두 동의해야 하는데, 1대만 살아있으면 장애 전환은 **일어나지 않음**. 한 대의 판단으로는 장애 전환을 승인할 수 없다는 게 핵심.
  - 참고: Sentinel 2대는 사실상 "모두 동의해야 하는" 구조라 장애 1대를 견딜 수 없음. 그래서 홀수 3대 이상을 씀. 3대 + quorum 2면 1대 장애를 견딤.

**추가 질문**: Sentinel 3대, quorum 2로 구성했다고 하자. 1대가 죽었을 때와 2대가 죽었을 때, 각각 Master 장애 시 자동 장애 전환이 일어날까? 이유도 같이 말해줘.

- **답변**: 1대가 죽으면 자동 전환이 가능하고, 2대가 죽으면 불가능하다. 1대가 죽으면 quorum 2일 가능성이 존재하고, 2대가 죽으면 영원히 일어날 수 없다.
- **멘토 피드백**: 결론 정확함. 다듬으면, 1대 장애 시에는 **살아있는 2대가 모두 Master 다운에 동의하면 quorum 2가 채워져서** 전환이 가능. 2대 장애 시에는 살아있는 1대가 혼자서 quorum을 채울 수 없어 전환이 막힘. "영원히"가 아니라 **Sentinel이 한 대라도 복구될 때까지** 막혀있는 것이고, 그 사이 Master가 죽어 있으면 쓰기는 계속 실패함.
- **정리**: Sentinel 3대 + quorum 2 = **1대 장애까지 견딤**, 2대 장애부터는 자동 복구가 멈춤. 이게 홀수 다수결 구성을 쓰는 이유.
