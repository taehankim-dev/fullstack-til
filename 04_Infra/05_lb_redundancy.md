# 05. 로드밸런서 자체의 이중화

## 0. 지난 세션들 복습
- App 서버: 여러 대로 늘려서 이중화 (01)
- 세션: Redis로 분리 (02), 그 Redis도 Replication + Sentinel로 이중화 (03), 용량/처리량은 Cluster로 샤딩 (04)
- 근데 지금까지 모든 그림에서 **맨 앞단의 로드밸런서(LB)는 항상 1대**였음

## 1. 문제 상황
- App 서버를 아무리 여러 대로 늘려놔도, 그 앞의 LB가 1대뿐이면 **LB가 서비스 전체의 진입점(entry point) 자체가 SPOF**가 됨
- LB가 죽으면 → 뒤에 App 서버가 10대 다 살아있어도 트래픽이 아예 들어올 방법이 없음 → 지금까지 쌓아온 이중화가 전부 무의미해짐

## 2. 해결 원리 - LB를 "또" 이중화하려면?
- 직관적으로 "LB 앞에 LB를 하나 더 두면 되지 않나?" 생각할 수 있는데, 그러면 그 앞의 LB가 또 SPOF가 되는 문제가 끝없이 반복됨 (무한 재귀)
- 그래서 LB 계층에서는 보통 **"IP 하나를 여러 대가 공유하고, 죽으면 다른 대가 그 IP를 가져간다"**는 다른 방식을 씀

### 방식: VIP(Virtual IP) + VRRP/Keepalived
- LB 2대(Active 1대, Standby 1대)가 **가상 IP(VIP) 하나를 같이 바라봄**
- 평소엔 Active가 VIP를 점유하고 트래픽을 받음. Standby는 Active와 주기적으로 **heartbeat**를 주고받으며 "살아있나?"만 감시
- Active가 죽으면(heartbeat 응답 없음) → Standby가 자동으로 그 VIP를 가져가서 자신이 트래픽을 받기 시작함
- 클라이언트/DNS 입장에서는 항상 **같은 IP(VIP)**로 요청하니까, 뒤에서 어느 LB가 실제로 응답하는지는 몰라도 됨 — 이게 핵심

### 참고: 클라우드 매니지드 LB라면?
- AWS ALB/NLB 같은 클라우드 제공 LB는 이미 여러 가용 영역(AZ)에 걸쳐 다중화되어 제공됨 — VRRP/Keepalived를 직접 구성할 필요가 없음
- 즉 "직접 Nginx/HAProxy로 LB를 구축"할 때만 이 이중화를 스스로 신경 써야 하고, 클라우드 매니지드 LB를 쓰면 이 부분은 플랫폼이 대신 해줌

## 3. 아키텍처 다이어그램

```
[DNS: service.com → VIP 1.2.3.4]
                |
         [VIP 1.2.3.4]  ← 가상 IP, LB 2대가 공유
           /         \
   [LB1: Active]    [LB2: Standby]
     (VIP 점유)        (heartbeat로 LB1 감시, 대기)
           |
      [App 서버 1] [App 서버 2] ...

LB1 장애 시 → heartbeat 끊김 감지 → LB2가 VIP를 가져감 → 트래픽이 LB2로 들어옴
(클라이언트는 여전히 같은 IP로 요청 중이라 변화를 모름)
```

## 4. 짚고 갈 한계
- Active-Standby 구조는 Standby가 평소엔 트래픽을 전혀 안 받고 대기만 함 — 자원을 "놀리는" 것처럼 보일 수 있음 (Active-Active도 가능하지만 구성이 더 복잡함)
- Failover 감지에도 heartbeat 주기만큼의 시간이 걸림 — 완벽히 0초 전환은 아니고, 아주 짧은 순단(blip)이 생길 수 있음
- 지난 Sentinel 세션에서 나온 **split-brain** 개념이 여기서도 똑같이 등장함 (아래 질문에서)

## 5. 아키텍처 설계 / 장애 시나리오 질문

**Q. LB1(Active)과 LB2(Standby) 사이의 heartbeat 네트워크 연결만 끊겼다고 하자. 둘 다 서버 자체는 멀쩡히 살아있고, 각자 "상대방이 죽었다"고 판단할 수 있는 상황이야.**
**이때 무슨 문제가 생길 수 있을까? (지난 Sentinel 세션에서 배운 개념과 연결해서 생각해봐.)**

- **답변**: Standby 로드밸런서가 Active가 죽었다고 판단하고 강제로 연결(VIP 점유)을 시도할 것 같다. 그러다 연결이 되면 두 로드밸런서 모두에 요청이 들어가서, 서버는 중복된 요청을 받게 되지 않을까?
- **멘토 피드백**: "둘 다 Active처럼 행동하려 한다"는 핵심(**split-brain**)은 정확히 짚었어. 다만 결과는 "중복 요청"이 아니라 좀 더 근본적인 문제야.
  - VIP는 하나의 IP 주소인데, 두 머신이 동시에 그 IP를 자기 것이라고 주장하면 이건 "요청이 두 곳에 똑같이 복제되는" 문제가 아니라 **네트워크 계층에서 그 IP가 누구 것인지에 대한 혼란(ARP 충돌)**이 생기는 문제임
  - 그 결과: 어떤 순간엔 트래픽이 LB1로, 어떤 순간엔 LB2로 들어가는 **일관성 없는 flapping**이 생김
  - 심하면 한 클라이언트의 TCP 연결 중간에 응답하는 쪽이 LB1→LB2로 바뀌면서 그 **연결 자체가 끊어짐**
  - 두 LB가 서로 다른 헬스체크 상태를 보고 있을 수도 있어서, 어떤 App 서버가 살아있다고 판단하는지도 LB1/LB2가 서로 다를 수 있음
  - 즉 split-brain의 진짜 문제는 "중복"이 아니라 **"어디로 갈지 예측 불가능해지는 혼란"**. 네트워크만 끊겼을 뿐 양쪽 서버 자체는 멀쩡히 살아있는 상황이 가장 다루기 까다로움
  - Sentinel이 "다수결(quorum)"로 이 문제를 막았던 것처럼, LB 이중화 솔루션들도 보통 split-brain을 막기 위한 별도 장치(외부 중재자, fencing 등)를 둠
