# 01. 단일 서버 구조의 한계와 로드밸런서 도입

## 0. 나의 현재 구조 (Before)

```
[사용자]
   |
   | HTTP/HTTPS
   v
[VM 1대 (Naver Cloud / 사내 리눅스)]
   ├─ Nginx (정적 파일 서빙 + 리버스 프록시)
   └─ App Server (Node.js/Express → PM2 관리, 또는 Spring Boot → Docker 컨테이너)
```

- 서버 1대에 모든 것이 올라가 있음
- 실제로는 스택별로 배포 방식이 다름: Node는 PM2, Spring Boot는 Docker → 하지만 이건 "같은 VM에 둘 다 얹혀있다"는 뜻이 아니라, **서비스/프로젝트마다 배포 전략이 다를 수 있다**는 의미. 로드밸런서 관점에서는 이 디테일이 중요하지 않으므로 앞으로 다이어그램은 "App Server" 한 박스로 단순화해서 다룸
- Nginx: 정적파일 서빙 + 백엔드로 프록시

## 1. 문제 상황 (트래픽 증가 / 장애 시나리오)

### 시나리오 A - 트래픽이 늘어날 때
- PM2 클러스터 모드든 Docker든, "한 VM의 CPU 코어/메모리/네트워크 대역폭" 이라는 물리적 한계 안에서만 스케일 가능 (도구가 서버 자체를 늘려주진 않음)
- 결국 "이 VM의 스펙을 올린다(Vertical Scaling)"는 방법밖에 없는데, 스펙업은 비용 대비 효율이 떨어지고 상한선이 있음

### 시나리오 B - 서버 자체가 죽었을 때 (SPOF: Single Point of Failure)
- Nginx나 PM2/Docker 같은 도구들은 "그 VM 안에서" 무중단을 챙겨주는 역할일 뿐, VM 자체가 죽으면(디스크 장애, OOM, 네트워크 단절, OS 패닉 등) 다 같이 사망
- 서비스 전체가 다운되고, 복구까지 사람이 개입해서 VM을 재기동하거나 새로 띄워야 함 → 다운타임 발생

→ 두 문제의 공통 원인: **"서버가 1대"** 라는 것 자체가 확장성과 가용성의 천장.

## 2. 해결 원리 - 왜 로드밸런서인가

핵심 아이디어는 단순함: **"서버를 여러 대로 늘리고, 앞단에서 트래픽을 분산해주는 존재를 둔다."**

- 지금까지는 Nginx가 "정적 파일 서빙 + 백엔드로 프록시" 역할을 VM 안에서 했다면,
- 이제는 그 앞에 **로드밸런서(LB)** 를 하나 더 두고, LB가 "여러 대의 백엔드 서버 중 어디로 요청을 보낼지" 결정하게 함
- 서버가 2대 이상이 되면:
  - 트래픽 증가 → 서버를 더 추가(Horizontal Scaling)해서 대응 가능
  - 서버 1대 장애 → LB가 헬스체크(Health Check)로 죽은 서버를 감지하고 트래픽을 안 보냄 → 나머지 서버가 계속 서비스

즉 로드밸런서는 단순히 "트래픽을 나눠주는 것"보다 **"장애 서버를 자동으로 우회시켜주는 것"** 이 실무에서 더 큰 가치임 (가용성 확보).

## 3. 아키텍처 다이어그램 (After)

```
                [사용자]
                   |
                   v
           [Load Balancer]   <-- 여기서 헬스체크 + 라우팅
             /          \
            /            \
    [VM 1 (App Server)]  [VM 2 (App Server)]
     Nginx(정적/프록시)     Nginx(정적/프록시)
     App(PM2 or Docker)    App(PM2 or Docker)
```

- 기존에 하던 "Nginx + PM2/Docker" 구성은 그대로 각 VM 안에 유지됨 (버릴 필요 없음)
- 달라지는 건 그 앞단에 트래픽을 분배해주는 계층이 하나 더 생긴다는 것

## 4. 로드밸런서 도입 시 새로 고민해야 할 것들 (다음 세션 예고용, 오늘은 깊게 안 다룸)

- 로그인 세션은 어느 서버에 저장하지? (서버가 2대인데 유저가 매번 다른 서버로 튈 수 있음)
- LB 자체도 1대면 그게 또 SPOF 아닌가?
- DB는 여전히 1대인데 이건 괜찮은가?
- VM을 미리 2대 사서 대기시켜야 하나, 트래픽 늘 때 자동으로 늘어나면 좋겠는데 (Auto Scaling)

## 5. 아키텍처 설계 / 장애 시나리오 질문

**Q. 지금 구조에서 로드밸런서 뒤에 App 서버를 2대로 늘렸다고 가정해보자.**
**사용자가 로그인해서 장바구니에 상품을 담았는데, 새로고침했더니 장바구니가 비어있다고 항의가 들어왔다.**
**왜 이런 일이 생겼을까? (지금 배운 "서버가 여러 대가 됐다"는 사실과 연결해서 생각해보기)**

- 답변: 세션이나 토큰이 공유되지 않았기 때문이다. 로드밸런서를 통해 요청이 분산되면서 사용자가 장바구니에 담은 상품이 공유되지 않았기 때문이다.
- 멘토 피드백: 정확함. 조금 더 정밀하게 말하면 — LB가 라운드로빈 등으로 요청마다 다른 VM에 보내는데, 세션은 기본적으로 각 서버의 "메모리"에 저장되기 때문에 발생하는 문제. VM1에 저장된 세션을 VM2는 모름. → 다음 세션 주제인 Sticky Session / Redis 세션 저장소 분리로 이어짐.
