# 04. Redis Cluster - 샤딩(Sharding)

## 0. 지난 세션 복습
- Sentinel은 **가용성**(Master가 죽어도 자동으로 Replica를 승격)을 해결해줌
- 근데 Sentinel 구조를 잘 보면: Master 1대 + Replica 여러 대 — **Replica는 Master와 똑같은 데이터의 복사본일 뿐**, 데이터를 나눠 갖는 게 아님
- 그래서 세션 데이터가 계속 늘어나서 **메모리 용량**이 모자라거나, 쓰기 요청이 너무 많아서 **Master 1대의 처리량**을 넘어서면, Sentinel 구조로는 못 풂 (Replica를 100대 늘려도 Master는 여전히 1대)

## 1. 문제 상황
- "서버 1대의 한계를 넘어서면 서버를 늘린다(Horizontal Scaling)"는 아이디어를 LB 세션에서 이미 써봤음
- Redis도 똑같은 문제를 겪음: **Master를 여러 대로 늘리고, 데이터를 나눠서 저장**해야 함 — 이게 **샤딩(Sharding)**

## 2. 해결 원리 - 해시 슬롯(Hash Slot)
- Redis Cluster는 전체 데이터 공간을 **16384개의 "슬롯(slot)"**으로 미리 쪼개놓음
- 키 하나가 들어오면 `CRC16(key) % 16384` 공식으로 "이 키는 몇 번 슬롯"인지 정해짐 (항상 같은 키 → 항상 같은 슬롯)
- 각 Master 노드가 슬롯의 **일부 구간**을 책임짐. 예: Master A는 0~5460번, B는 5461~10922번, C는 10923~16383번
- 클라이언트는 키의 슬롯을 계산해서, 그 슬롯을 담당하는 Master로 직접 요청. 엉뚱한 노드로 요청하면 `MOVED <slot> <올바른 노드 주소>` 응답을 받고 재요청함

## 3. 가용성은 어떻게? (지난 세션과 결합)
- Cluster 모드에서는 Sentinel을 따로 안 씀 — **Cluster 자체에 내장된 장애 감지/투표** 기능이 있음
- 각 Master는 자기만의 Replica를 둘 수 있고, 그 Master가 죽으면 **그 Master가 담당하던 슬롯 구간**만 Replica가 승격해서 이어받음 (다른 Master/슬롯 구간은 영향 없음)
- 정리하면: **Cluster = 데이터를 쪼개서 용량/처리량을 늘리는 것(샤딩) + 각 조각마다 지난 세션에서 배운 자동 장애 전환(HA)을 붙인 것**

## 4. 아키텍처 다이어그램

```
전체 해시 슬롯: 0 ~ 16383 (키마다 CRC16(key) % 16384로 슬롯 결정)

[Master A]            [Master B]            [Master C]
 slots 0~5460          slots 5461~10922       slots 10923~16383
    | 복제                  | 복제                  | 복제
[Replica A1]           [Replica B1]           [Replica C1]

클라이언트 → 키의 슬롯 계산 → 담당 Master로 직접 요청
(잘못된 노드로 가면 "MOVED <slot> <올바른 노드>" 받고 재요청)

Master B 장애 시 → Replica B1만 Master로 승격 (A, C 영향 없음)
```

## 5. 짚고 갈 한계
- 여러 키를 동시에 다루는 연산(예: `MGET key1 key2`, 트랜잭션, Lua 스크립트)은 그 키들이 **같은 슬롯**에 있어야 동작함. 서로 다른 Master에 걸쳐있으면 에러가 남
  - 해결책: **해시 태그(hash tag)** — 키 이름에 `{...}` 부분을 넣으면 그 부분만 슬롯 계산에 사용함 (예: `session:{user123}:cart`, `session:{user123}:profile` → 둘 다 `user123` 부분만 해시해서 같은 슬롯에 들어가게 강제 가능)
- 노드를 늘리거나 줄일 때 슬롯 구간을 재배치(resharding)해야 하는데, 운영 중에 신경 쓸 거리가 생김
- Sentinel과 목적이 다름: **Sentinel = 하나의 데이터셋을 안 죽게 하는 것**, **Cluster = 데이터셋 자체를 쪼개서 용량/처리량을 늘리는 것** (+ 쪼개진 각 조각의 가용성)

## 6. 아키텍처 설계 / 장애 시나리오 질문

**Q. 한 사용자의 "세션 정보"와 "장바구니 정보"를 Redis에 각각 별도의 키로 저장하고 있는데, 이 둘을 하나의 트랜잭션(또는 Lua 스크립트)으로 묶어서 한 번에 처리해야 하는 로직이 생겼다고 하자.**
**Redis Cluster 환경이라면, 이 두 키를 설계할 때 무엇을 신경 써야 할까?**

(힌트: 두 키가 다른 Master에 떨어지면 무슨 일이 생기는지 떠올려봐.)

- **답변**: 처리 순서 보장이 필요할 것 같다. 아니면 같은 슬롯에 존재하도록 만들어서 둘을 처리하도록 보장해야 할 것 같다.
- **멘토 피드백**: 두 번째가 정답. 첫 번째("순서 보장")는 방향이 살짝 다름 — 문제는 순서가 꼬이는 게 아니라, 두 키가 다른 Master(슬롯)에 떨어지면 트랜잭션/Lua 스크립트 자체가 **실행이 안 되고 `CROSSSLOT` 에러**가 난다는 것. 그래서 키 설계 시 **해시 태그**로 강제로 같은 슬롯에 몰아넣어야 함:
  ```
  session:{user123}:profile
  session:{user123}:cart
  ```
  `{user123}` 부분만 해시 계산에 쓰여서, 두 키가 항상 같은 슬롯(같은 Master)에 들어가 트랜잭션/Lua 스크립트가 정상 동작함.
