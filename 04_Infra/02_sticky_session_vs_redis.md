# 02. 세션 불일치 문제 해결 - Sticky Session vs Redis 세션 저장소

## 0. 지난 세션에서 발견한 문제 (복습)
- 로드밸런서가 요청마다 다른 서버로 라우팅함
- 근데 세션은 기본적으로 각 서버(VM)의 "메모리"에 저장됨
- 그래서 사용자가 VM1에 로그인/장바구니 담기 → 다음 요청이 VM2로 감 → VM2는 그 세션을 모름 → 로그아웃되거나 장바구니가 빔

## 1. 해결책 A: Sticky Session (세션 고정)
- **원리**: LB가 "이 사용자는 항상 같은 서버로 보낸다"고 고정해버림 (보통 쿠키 기반, 혹은 클라이언트 IP 해시 기반)
- **장점**: 앱 코드나 아키텍처를 안 건드리고 LB 설정만으로 바로 해결 가능
- **단점**:
  - 트래픽이 골고루 안 퍼질 수 있음 (특정 서버에 사용자가 몰리면 그 서버만 부하)
  - **그 서버가 죽으면?** → 그 서버에 고정되어 있던 사용자들의 세션은 그냥 증발함. "서버 1대가 SPOF"였던 문제가 "서버 여러 대 중 하나가 SPOF"로 축소됐을 뿐, 근본적으로는 안 풀림
  - 오토스케일링(서버를 늘리거나 줄이는 것)과 궁합이 안 좋음 — 서버 구성이 바뀌면 "누구를 어디로 고정했었는지"가 꼬임

## 2. 해결책 B: 세션 저장소 분리 (Redis)
- **원리**: 세션 데이터를 각 서버의 "로컬 메모리"가 아니라, 모든 서버가 공유하는 **외부 중앙 저장소**(대표적으로 Redis)에 저장
- 이제 서버는 요청이 오면 "이 세션이 어디 있지?"를 고민할 필요 없이, 항상 같은 곳(Redis)에 물어봐서 세션을 가져옴 → **어떤 서버로 요청이 가든 상관없어짐**
- 이게 바로 **"Stateless 서버"** 원칙의 핵심: 서버 자체는 상태(state)를 안 갖고, 상태는 외부에 위임 → 서버를 자유롭게 늘리거나 줄이거나 하나가 죽어도 문제 없음. 진짜 수평 확장(Horizontal Scaling)이 가능해지는 전제 조건
- **장점**: 아키텍처적으로 올바름, LB가 트래픽을 완전히 자유롭게 분산 가능, 오토스케일링과 궁합 좋음
- **단점**: Redis라는 새로운 컴포넌트가 생김 → 이번엔 Redis 자체의 안정성을 신경 써야 함 (오늘은 일단 "이렇게 하면 문제가 풀린다"까지만, Redis 자체가 또 SPOF가 될 수 있다는 건 다음 세션에서)

## 3. 비교

| | Sticky Session | Redis 세션 저장소 |
|---|---|---|
| 구현 난이도 | 낮음 (LB 설정만) | 중간 (Redis 도입 + 코드 수정) |
| 서버 1대 장애 시 | 그 서버에 고정된 유저만 로그아웃 | 영향 없음 (Redis만 살아있으면) |
| 오토스케일링 궁합 | 안 좋음 | 좋음 |
| 근본적 해결 여부 | ✗ (임시방편) | ✓ |

## 4. 아키텍처 다이어그램

```
[Sticky Session]

[사용자A] ──┐
            ├─→ [LB: 쿠키/IP로 고정 라우팅] ──→ A는 항상 [VM1]
[사용자B] ──┘                              └──→ B는 항상 [VM2]


[Redis 세션 저장소 분리]

[사용자A] ──┐
            ├─→ [LB: 자유롭게 라운드로빈] ──→ [VM1] 또는 [VM2] (아무 서버나 OK)
[사용자B] ──┘                                    │         │
                                                  └────┬────┘
                                                        ▼
                                                 [Redis: 세션 저장소]
                                              (모든 서버가 여기서 세션 조회)
```

## 5. 아키텍처 설계 / 장애 시나리오 질문

**Q. Redis 세션 저장소를 도입해서 "서버가 여러 대여도 세션이 일관된다"는 문제는 해결했다고 하자.**
**그런데 만약 이 Redis 서버 자체가 다운되면 어떻게 될까? 지금 구조에서 그 영향 범위(얼마나 심각한 장애가 되는지)는 어느 정도일까?**

(힌트: 세션 문제를 "서버 여러 대"에서 "Redis 한 대"로 옮겨온 것뿐이라면, 이게 무슨 의미인지 생각해봐.)

- **답변**: 모든 세션(로그인, 장바구니 등)이 소실된다. Sticky Session에서 서버 1대가 죽는 것보다 영향이 더 크다.
- **멘토 피드백**: 방향 정확함. 정밀하게 말하면 이건 "더 크다" 정도가 아니라 **장애의 성격 자체가 다름**: Sticky Session은 죽은 서버에 물린 사용자만 영향받는 **부분 장애**인데, Redis는 모든 서버가 공통으로 의존하는 단일 지점이라 죽으면 **전체 사용자가 동시에** 영향받는 **전면 장애**. 결국 "분산돼 있던 장애 지점"을 "하나의 새로운 중앙 SPOF(Redis)"로 모아버린 셈. (완전 소실 vs 일시적 서비스 중단 여부는 Redis의 persistence 설정/복제본 유무에 따라 달라짐 → 다음 세션 주제.)
