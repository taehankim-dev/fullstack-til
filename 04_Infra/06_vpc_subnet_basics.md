# 06. VPC / 서브넷 기초

## 0. 지난 세션들 복습
- LB, App 서버, Redis를 각각 여러 대로 늘려왔는데, 지금까지 다이어그램에서는 이 서버들을 그냥 박스로만 그렸음
- 실제 클라우드에서는 이 서버들이 **어떤 네트워크 공간 안에** 배치되는지가 중요해짐 — 오늘은 그 네트워크 구조를 다룸
- (네이버클라우드 VM에 SSH로 접속해서 썼던 경험 있지? 그 VM도 사실 어떤 네트워크 안에 속해 있었는데, 보통 기본 네트워크가 자동으로 제공돼서 신경 쓸 일이 없었던 것뿐임)

## 1. 문제 상황
- 서버가 1~2대일 때는 "그냥 각 서버에 방화벽(보안 그룹) 설정해서 막으면 되지 않나?" 싶을 수 있음
- 근데 서버 역할이 LB / App / Redis / DB로 다양해지면: **LB는 외부에서 접근돼야 하고, Redis/DB는 외부에서 절대 접근되면 안 됨**이라는 요구사항이 생김
- 모든 서버를 "인터넷에 붙어있는 개별 VM들"로 두고 방화벽 설정만으로 막으려 하면: 설정이 복잡해지고, 담당자가 설정 하나를 깜빡하면 **DB가 인터넷에 그대로 노출되는 대참사**가 날 수 있음 (실제로 이런 사고가 뉴스에 꽤 나옴)
- → 필요한 것: "설정을 깜빡해도 구조적으로 안전한" 네트워크 분리

## 2. 해결 원리 - VPC와 서브넷
- **VPC(Virtual Private Cloud)**: 클라우드 안에 만드는 "내 전용 가상 네트워크 공간". 다른 사람의 서버와는 네트워크적으로 완전히 분리된, 나만의 울타리라고 생각하면 됨
- **서브넷(Subnet)**: 그 VPC를 역할별로 나눈 작은 구역
  - **Public Subnet**: Internet Gateway(인터넷과 연결해주는 통로)로 가는 길이 열려있음 → 외부에서 접근 가능 → **LB**가 여기 위치
  - **Private Subnet**: Internet Gateway로 가는 길이 없음 → 외부에서 아예 접근 불가능 (주소조차 안 보임) → **App 서버, Redis, DB**가 여기 위치
- 핵심은: Public이냐 Private이냐는 "물리적으로 다른 네트워크"가 아니라, **"Internet Gateway로 나가는 라우팅 테이블이 연결되어 있는가"**라는 설정의 차이일 뿐임

## 3. 아키텍처 다이어그램

```
[Internet]
    |
[Internet Gateway]
    |
========== VPC (10.0.0.0/16) ==========================
|                                                      |
|  [Public Subnet 10.0.1.0/24]                         |
|     [LB1] [LB2]   ← 외부에서 접근 가능                  |
|                                                      |
|  [Private Subnet 10.0.2.0/24]                        |
|     [App 서버1] [App 서버2]  ← 내부에서만 접근 가능        |
|                                                      |
|  [Private Subnet 10.0.3.0/24]                        |
|     [Redis Cluster] [DB]  ← 완전히 내부, 외부 노출 X      |
=========================================================
```
(`10.0.0.0/16` 같은 표기는 "이 네트워크에서 쓸 수 있는 IP 범위"를 나타내는 것 정도로만 오늘은 가볍게 짚고 넘어갈게.)

## 4. 짚고 갈 것
- Private Subnet에 있는 서버도 가끔 "나가는" 인터넷 요청(예: OS 패키지 업데이트, 외부 API 호출)이 필요할 수 있음 → 이건 Public Subnet에 **NAT Gateway**를 두면, Private 서버가 그걸 통해 "나가기만" 가능해짐 (들어오는 요청은 여전히 막혀있음). 오늘은 개념만 짚고, 다음 세션 후보로 남겨둠
- Public/Private 분리는 "보안 그룹 설정을 깜빡해도" 구조적으로 막아주는 **방어선 하나를 더 두는 것** — 보안 그룹이 1차 방어선이라면 서브넷 분리는 0차 방어선인 셈

## 5. 아키텍처 설계 / 장애 시나리오 질문

**Q. Redis Cluster가 Private Subnet에 있다는 건, 외부 인터넷에서는 그 IP로 아예 접근이 안 된다는 뜻이야.**
**그런데 네가 운영 중인 Redis에 직접 접속해서 데이터를 확인하거나 디버깅하고 싶다면 (네 개발 PC에서), 어떻게 접근할 수 있을까?**

(힌트: Private Subnet 서버에 "내가"는 접근해야 하는데, "아무나"는 안 되게 하려면 뭔가 중간에 하나를 거쳐야 하지 않을까?)

- **답변**: 잘 모르겠음 (처음 접하는 개념)
- **멘토 설명**: **Bastion Host(점프 서버)** 개념을 쓰면 됨.
  - Public Subnet에 딱 1대, 접근이 엄격히 제한된(SSH 키 인증, 특정 IP만 허용 등) 작은 VM을 둠
  - 외부에서는 이 Bastion에만 SSH 접속 가능. Private Subnet의 Redis/DB는 여전히 인터넷에서 직접 안 보임
  - 접속 흐름: 내 PC → (SSH) → Bastion → (SSH, 같은 VPC 내부라 가능) → Redis/DB
  - 핵심 전략: "모든 Private 서버를 하나씩 열어주기"가 아니라 "엄격하게 감시되는 문 하나만 열어두고 그 문을 통해서만 들어가게" 하는 것 → 설정 실수로 뚫릴 위험을 문 하나로 집중시킴
  - 실제 접속은 보통 **SSH 터널링(포트 포워딩)**으로 함: 내 PC의 `localhost:6380`을 Bastion을 경유해서 Redis의 Private IP:6379로 연결해두면, 로컬에서 `localhost:6380`에 접속하는 것처럼 Redis 클라이언트를 쓸 수 있음
  - 참고: 팀 전체가 상시로 Private 네트워크에 접근해야 하면 Bastion보다 **VPN**(예: AWS Client VPN)으로 내 PC를 VPC에 가상으로 "참여"시키는 방식을 씀. Bastion은 가끔 한 명이 드나드는 문, VPN은 팀 전체가 쓰는 상시 통로에 가까움
