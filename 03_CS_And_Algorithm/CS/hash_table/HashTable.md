# 해시테이블 직접 구현

## 1. 문제 정의 및 실무 맥락
- 지금까지 `Map`/`Object`를 "조회가 O(1)인 도구"로만 써왔는데, 그 내부가 실제로 어떻게 동작하는지는 다루지 않았음. 오늘은 그 내부 원리인 **해시테이블**을 직접 구현해봄.
- 사실 이미 비슷한 걸 본 적 있음 — Redis Cluster 세션에서 `CRC16(key) % 16384`로 "이 키가 몇 번 슬롯인지" 정했었잖아. 이게 바로 해시테이블의 핵심 원리: **해시 함수로 큰 키 공간을 작은 배열 인덱스(버킷) 범위로 눌러 담는 것**.
- 문제는, 키는 무한히 많은데 배열 칸(버킷)은 한정돼 있어서 **서로 다른 두 키가 같은 버킷에 매핑되는 충돌(collision)이 필연적으로 발생**함 (비둘기집 원리). 이 충돌을 어떻게 처리하느냐가 해시테이블 구현의 핵심.
- 실무 연결: JS의 `Object`/`Map` 내부도 해시테이블 기반이고, 충돌 처리 전략이 부실하면 "악의적으로 충돌을 유도하는 키들을 대량으로 보내서 O(1)이던 조회를 O(n)으로 떨어뜨리는" HashDoS 같은 공격이 실제로 존재함.
- 오늘은 충돌 처리 방식 중 가장 직관적인 **체이닝(Chaining)**: 각 버킷을 "배열(또는 리스트)"로 만들어서, 같은 버킷에 매핑된 키들을 그 안에 여러 개 쌓아두는 방식으로 구현.

## 2. 구현 요구사항
이번엔 요구사항을 실행 가능한 테스트로 미리 준비해뒀어. `03_CS_And_Algorithm/CS/hash-table.ts`에 아래 뼈대가 있고, `hash-table.test.ts`의 테스트를 통과시키면 돼. (`hash()` 메서드는 이미 구현해뒀어 — 오늘의 초점은 해시 함수 자체가 아니라 **충돌 처리**니까.)

```typescript
export class HashTable<V> {
  private buckets: Array<Array<[string, V]>>;

  constructor(private bucketCount: number = 8) {
    this.buckets = Array.from({ length: bucketCount }, () => []);
  }

  private hash(key: string): number {
    let hash = 0;
    for (let i = 0; i < key.length; i++) {
      hash = (hash * 31 + key.charCodeAt(i)) % this.bucketCount;
    }
    return hash;
  }

  // key-value를 저장. 같은 key로 또 set하면 "추가"가 아니라 "값 갱신"이어야 함
  set(key: string, value: V): void {
    throw new Error("not implemented");
  }

  // key에 해당하는 value를 반환. 없으면 undefined
  get(key: string): V | undefined {
    throw new Error("not implemented");
  }

  // key를 제거. 제거했으면 true, 원래 없었으면 false
  delete(key: string): boolean {
    throw new Error("not implemented");
  }
}
```

**제약조건**
- `set`/`get`/`delete` 모두 "해당 버킷 안에서만" 탐색하도록 구현 (버킷 찾기는 O(1), 버킷 안에서 키 찾기는 그 버킷에 쌓인 개수만큼 — 이게 왜 "평균 O(1), 최악 O(n)"인지와 연결됨)
- 같은 key로 `set`을 두 번 호출하면 버킷 안에 중복으로 쌓이지 않고 **값만 갱신**되어야 함
- `npm test` (레포 루트에서) 로 테스트를 돌려서 확인

## 참고: 테스트 파일
```typescript
// hash-table.test.ts 미리보기 (일부)
it("같은 버킷에 여러 키가 충돌해도 각각 올바르게 조회된다", () => {
  const table = new HashTable<number>(1); // 버킷 1개 = 모든 키가 강제로 충돌
  table.set("a", 1);
  table.set("b", 2);
  table.set("c", 3);

  expect(table.get("a")).toBe(1);
  expect(table.get("b")).toBe(2);
  expect(table.get("c")).toBe(3);
});
```

## 3. 내가 작성한 코드
실제 구현은 [hash-table.ts](./hash-table.ts) 참고. `npm test`로 [hash-table.test.ts](./hash-table.test.ts)의 테스트 14개(머지소트 포함) 전부 통과 확인함.

체이닝 방식으로 `set`/`get`/`delete` 모두 "해당 버킷을 찾은 뒤, 그 버킷 배열을 선형 탐색"하는 동일한 패턴으로 구현:
- `set`: 버킷 안에서 같은 key를 찾으면 값 교체, 못 찾으면 `push`로 새로 추가
- `get`: 버킷 안에서 같은 key를 찾으면 값 반환, 못 찾으면 `undefined`
- `delete`: 버킷 안에서 같은 key를 찾으면 `splice`로 제거하고 `true`, 못 찾으면 `false`

## 4. 코드 리뷰 피드백

**최종 코드는 정확함.** (충돌을 강제로 유도한 테스트까지 포함해서 전부 통과)

1. **(가독성, 선택) 안 쓰는 구조분해 변수** — `set`/`delete`에서 `const [currentKey, currentValue] = bucket[i]`로 구조분해하는데 `currentValue`는 안 씀. `bucket[i][0] === key`로 써도 되고, 지금처럼 둬도 동작엔 문제없음.
2. **(엣지케이스, 참고) `bucketCount <= 0`** — `hash()`에서 `% 0`이 `NaN`이 되어 `buckets[NaN]`이 `undefined`라서 `bucket.length`에서 런타임 에러. 요구사항에 없던 케이스라 지금 수정 필요는 없음 (LRU `capacity <= 0` 때와 동일하게 선택적으로 남겨둠).

**복잡도**: `set`/`get`/`delete` 모두 버킷 찾기 O(1) + 버킷 내 선형 탐색 — **평균 O(1)**(키가 버킷에 고르게 분산된다는 가정), **최악 O(n)**(한 버킷에 전부 몰릴 때, 충돌 테스트처럼).

## 5. 꼬리질문과 답변

### 1. 버킷 하나에 키가 수백 개씩 쌓이면 무슨 일이 생기고, 실제 해시테이블은 이걸 어떻게 막을까?

- **답변**: 조회/변경/삭제에 오랜 시간이 걸릴 것 같다. 실제 해시테이블은 한 버킷에 너무 많이 쌓이지 않도록 분배하는 작업이 있을 것 같다.
- **정리**: 정확함. 이걸 **리사이징(Resizing) + 재해싱(Rehashing)**이라고 함. "로드 팩터(전체 키 수 / 버킷 수)"가 일정 기준(보통 0.75)을 넘으면 버킷 배열을 더 크게(보통 2배로) 새로 만들고, 기존 키 전부를 새 버킷들에 다시 분산시킴. 평소엔 O(1)을 유지하다가 가끔 O(n)짜리 큰 작업으로 균형을 되찾는다는 점에서, BST의 "재조정(rebalancing)"과 같은 역할.

### 2. HashDoS 공격(의도적으로 같은 버킷에 몰리는 키들을 대량 전송)을 당하면 어떻게 되고, 어떻게 막을까?

- **답변**: 한 버킷이 포화돼서 조회/수정이 오래 걸릴 것 같다. 한 버킷에 너무 많은 키가 몰리지 않도록 균등 분배하는 방식을 고려해야 할 것 같다.
- **정리**: 증상 설명은 정확하지만, "균등 분배(리사이징)"로는 이 공격을 못 막음 — 공격자가 해시 알고리즘을 알고 있다면, 버킷을 몇 개로 늘리든 그 크기에 맞춰 충돌하는 키를 다시 계산해서 보낼 수 있기 때문. 리사이징은 "우연한 충돌"엔 효과적이지만 "의도된 공격"에는 무력함.
  - **진짜 방어책**: 해시 함수에 **공격자가 모르는 무작위 seed(salt)**를 섞는 것. 해시테이블 생성 시(또는 프로세스마다) 무작위 seed를 하나 만들어 해시 계산에 포함시키면, 공격자가 알고리즘은 알아도 seed를 모르니 충돌을 미리 계산해둘 수 없음. Python(3.3+), Java, Node.js 같은 런타임이 실제로 이 "해시 seed 랜덤화"를 HashDoS 방어로 사용함.
  - **보너스**: Java의 `HashMap`은 한 버킷의 체인이 너무 길어지면(보통 8개 이상) 그 버킷을 배열이 아니라 **균형 트리(Red-Black Tree)**로 전환함 — 최악의 경우에도 O(n) 대신 O(log n)으로 떨어짐. 지난 BST 세션 내용이 실제로 이렇게 쓰임.

## 6. 면접용 설명 요약
> `Map`/`Object`가 왜 평균적으로 O(1) 조회가 되는지 이해하려고 해시테이블을 직접 구현해봤습니다. 핵심 원리는 해시 함수로 키를 버킷(배열 인덱스)에 매핑하는 것인데, 키 공간은 무한하고 버킷은 한정적이라 서로 다른 키가 같은 버킷에 매핑되는 충돌이 필연적으로 발생합니다. 저는 충돌 처리 방식 중 체이닝(각 버킷을 배열로 두고 충돌한 키들을 그 안에 쌓는 방식)으로 `set`/`get`/`delete`를 구현했고, 일부러 버킷 1개로 모든 키를 충돌시키는 테스트까지 통과시켜 검증했습니다.
>
> 이 구조의 복잡도는 평균 O(1), 최악 O(n)입니다. 실제 해시테이블은 이 최악의 경우를 두 가지 방식으로 완화합니다. 첫째, 우연한 충돌이 쌓여 로드 팩터가 높아지면 버킷 배열을 리사이징하고 기존 키를 재해싱하는데, 이는 BST의 재조정(rebalancing)과 같은 역할입니다. 둘째, 공격자가 의도적으로 같은 버킷에 몰리는 키들을 대량으로 보내는 HashDoS 공격은 리사이징만으로는 못 막는데, 이건 해시 알고리즘이 공개되어 있으면 버킷 수가 바뀌어도 공격자가 다시 충돌 키를 계산할 수 있기 때문입니다. 이에 대한 실제 방어책은 해시 함수에 공격자가 모르는 무작위 seed를 섞는 것이며, Java의 `HashMap`처럼 한 버킷이 너무 커지면 균형 트리로 전환해 최악의 경우도 O(log n)으로 낮추는 방식도 실무에서 쓰입니다.
