# AI 오케스트레이션 - 여러 단계를 잇는 파이프라인
| 여러 AI 모델, 외부 도구, 프롬프트 등을 하나의 파이프라인으로 엮어 조율함으로 복잡한 목표를 자동화하고 정확도를 높이는 기술 및 워크플로우.

## 1. 문제 정의 및 실무 맥락
- 면접에서 "AI 오케스트레이션"이 나왔다면, 보통 "특정 프레임워크(LangChain 등)를 아는지"를 묻는 게 아니라 **"여러 개의 독립적이고 불안정한 단계를 하나의 안정적인 흐름으로 조합할 수 있는지"**를 묻는 걸 가능성이 높음. 백엔드 엔지니어 입장에서는 결국 "여러 비동기 작업을 순서대로 엮고, 각 단계의 실패/지연을 다루는 설계 문제"임.
- 전형적인 AI 파이프라인: **검색(Retrieve, 벡터 DB 등) → 프롬프트 구성/LLM 호출(Generate) → 후처리(Post-process)**. 지난 벡터 검색 세션이 첫 단계였고, 오늘은 이 전체를 묶어주는 "오케스트레이션 레이어"를 다룸.
- 문제: 각 단계가 독립적으로 느리거나 실패할 수 있음 — LLM API 응답이 느릴 수도, 벡터 DB가 타임아웃 날 수도, 특정 단계만 실패해도 전체를 멈추면 안 되는 경우도 있음. 이건 지난 **"하드웨어 커맨드 큐 + 서킷 브레이커"** 세션에서 다룬 "불안정한 외부 시스템과 어떻게 안전하게 통신하는가"와 본질적으로 같은 문제임 — 대상이 하드웨어에서 "LLM API/외부 서비스"로 바뀐 것뿐.
- 오늘은 여러 단계(step)를 순서대로 실행하면서, 각 단계에 **타임아웃**, **재시도**, 그리고 "이 단계가 끝까지 실패하면 전체를 중단할지 건너뛰고 계속할지"를 설정할 수 있는 작은 **파이프라인 오케스트레이터**를 직접 구현해볼 것.

## 2. 구현 요구사항
```typescript
export type Context = Record<string, any>;
export type Step = (ctx: Context) => Promise<void>;

export interface StepOptions {
  timeoutMs?: number;       // 설정 시, 이 시간 안에 안 끝나면 실패로 간주
  retries?: number;         // 실패 시 추가 재시도 횟수 (기본 0 — 총 시도 횟수 = 1 + retries)
  onError?: "fail" | "skip"; // 재시도까지 다 썼는데도 실패하면: 전체 중단(fail, 기본값) 또는 건너뛰고 계속(skip)
}

export class Pipeline {
  // 스텝을 순서대로 등록. 체이닝 가능하도록 this 반환.
  addStep(step: Step, options?: StepOptions): this {}

  // 등록된 스텝들을 순서대로 실행하면서 ctx를 계속 변형해나감. 최종 ctx를 반환.
  async run(initialCtx: Context): Promise<Context> {}
}
```

**요구사항**
- 각 스텝은 `ctx`를 직접 변경하는 방식 (Express 미들웨어가 `req`/`res`를 변경하는 것과 비슷한 패턴).
- `timeoutMs`가 설정된 스텝은 그 시간 안에 끝나지 않으면 실패로 처리 (`Promise.race` 같은 방식 고려).
- 실패 시 `retries`에 설정된 횟수만큼 추가로 재시도.
- 재시도까지 다 썼는데도 실패하면 `onError`에 따라: `"fail"`(기본값)이면 `run()` 전체가 에러를 던지고, `"skip"`이면 그 스텝만 건너뛰고 다음 스텝으로 진행.

**테스트 예시** (일부는 `03_CS_And_Algorithm/CS/ai_pipeline_orchestration/pipeline.test.ts`에 이미 작성해둠)
```typescript
const pipeline = new Pipeline();
pipeline.addStep(async (ctx) => { ctx.a = 1; });
pipeline.addStep(async (ctx) => { ctx.b = ctx.a + 1; });
await pipeline.run({});
// { a: 1, b: 2 }
```

## 3. 내가 작성한 코드
실제 구현은 [pipeline.ts](./pipeline.ts) 참고. `npm test`로 [pipeline.test.ts](./pipeline.test.ts) 포함 전체 테스트 30개 통과, `npx tsc --noEmit`으로 타입 에러 없음 확인함.

- `addStep`: 스텝과 옵션을 배열에 저장, `this` 반환으로 체이닝 가능.
- `run`: 스텝마다 `1 + retries`번까지 시도 → 전부 실패하면 `onError`에 따라 `continue`(skip) 또는 `throw`(fail).
- `runWithTimeout`: `timeoutMs`가 있으면 `Promise.race([step(ctx), timeoutPromise])`로 제한시간 적용.

## 4. 코드 리뷰 피드백

**최종 코드는 정확함.** 과정에서 두 가지 실전형 문제를 겪고 고쳤음.

1. **(치명적 버그, 발견 후 스스로 수정) `clearTimeout` 타이밍** — `async` 함수에서 `return Promise.race(...)`처럼 `await` 없이 반환하면, 그 Promise가 끝나길 기다리지 않고 즉시 `finally`로 넘어감. 그래서 `clearTimeout`이 타이머 생성 직후 거의 바로 실행돼버려 **타임아웃 기능 자체가 무력화**되는 버그였음. `return await Promise.race(...)`로 고쳐서 해결 — `try` 블록이 race가 실제로 끝날 때까지 안 끝나게 만듦.
2. **(타입 에러, 원인 진단 후 해결) `Promise<never>` + Definite Assignment Assertion** — resolve 없이 reject만 하는 Promise는 타입을 `Promise<never>`로 명시해야 `Promise.race`의 결과 타입이 깨끗하게 유지됨. 이때 `let timeout: NodeJS.Timeout`처럼 타입을 명시하면 "Variable used before being assigned" 에러가 나는데, 이는 TS가 `new Promise(executor)`의 `executor`가 **생성 즉시 동기 실행**된다는 걸 추론하지 못해서임. `let timeout!: NodeJS.Timeout`(definite assignment assertion, `!`)으로 "내가 보장한다"고 명시해서 해결. (반환 타입을 `Promise<unknown>`으로 느슨하게 바꿔서 에러를 피하는 건 타입 안정성을 희생하는 잘못된 해결 방향이었음 — 더 정확한 방법으로 수정.)

**복잡도**: 스텝당 최대 `1 + retries`번 시도 → 전체는 O(스텝 수 × 재시도 수)에 비례. 공간은 O(1) 추가 (ctx 자체는 공유 참조).

**참고(엣지케이스, 코드 수정 불필요)**: `timeoutMs`로 "포기"한 스텝의 원래 비동기 작업(`step(ctx)`) 자체는 JS에서 진짜로 취소되지 않고 백그라운드에서 계속 실행됨 — `Promise.race`는 "결과를 기다리는 것만 그만둘" 뿐, 원래 Promise를 중단시키진 않음. 테스트의 `neverSet` 케이스가 이걸 보여줌.

## 5. 꼬리질문과 답변

### 1. 외부 효과를 일으키는 스텝이 실패 직전에 이미 그 효과를 일으켰는데 재시도로 처음부터 다시 실행하면?

- **답변**: 다른 요청들이 큐에 쌓이면서 대기 시간이 길어지고, 서버가 다운될 수도 있을 것 같다.
- **정리**: 방향이 다름 — 이건 일반적인 부하 문제고, 실제로 노리는 포인트는 **멱등성(idempotency)**. 예: "결제 요청" 스텝이 외부 API에 이미 요청을 보냈고 실제로 처리됐는데, 응답을 받기 직전에 타임아웃나면, 재시도가 그 스텝을 처음부터 다시 실행해서 **결제가 중복 처리**될 수 있음. 지난 하드웨어 커맨드 큐 세션의 "재전송 시 하드웨어가 중복 실행하는 위험"과 같은 문제 — 멱등성 키를 붙이거나 재시도 가능한 작업만 재시도해야 함.

### 2. 타임아웃으로 포기한 스텝이 백그라운드에서 계속 실행되다가 나중에 ctx를 건드리면?

- **답변**: 이전 작업이 현재 작업에 영향을 줘서 ctx 필드가 바뀌고, 다른 실행 방향으로 진행될 수 있을 것 같다.
- **정리**: 정확함. 파이프라인이 이미 다음 스텝(들)로 넘어간 뒤에, 포기했던 스텝이 뒤늦게 같은 `ctx` 필드를 덮어쓸 수 있음. 공유 자원(`ctx`)에 서로 다른 시점의 흐름이 동시에 접근하는 **race condition**과 같은 구조.

## 6. 면접용 설명 요약
> 면접에서 나온 "AI 오케스트레이션"은 특정 프레임워크를 아는지가 아니라, 검색·LLM 호출·후처리처럼 여러 개의 독립적이고 불안정한 단계를 하나의 안정적인 파이프라인으로 조합할 수 있는지를 묻는 질문이라고 이해했습니다. 그래서 각 스텝에 타임아웃, 재시도, 그리고 "실패 시 전체를 중단할지 건너뛰고 계속할지"를 설정할 수 있는 작은 파이프라인 오케스트레이터를 직접 구현해봤습니다.
>
> 구현하면서 두 가지 실전형 문제를 겪었습니다. 첫째, `async` 함수에서 `await` 없이 Promise를 반환하면 `finally`가 그 Promise가 끝나기 전에 실행돼서, 타임아웃 타이머를 정리하는 로직이 타이머 생성 직후 바로 실행되어 타임아웃 기능 자체가 무력화되는 버그가 있었습니다. 둘째, resolve 없이 reject만 하는 Promise의 타입을 `never`로 명시하는 과정에서, TypeScript가 Promise 생성자의 콜백이 즉시 동기 실행된다는 걸 추론하지 못해 "사용 전 할당" 에러가 났는데, definite assignment assertion으로 해결했습니다.
>
> 설계상 중요하게 짚은 점은 두 가지입니다. 재시도가 이미 외부에 효과를 일으킨 작업(예: 결제 요청)을 처음부터 다시 실행하면 중복 처리가 될 수 있어서 멱등성을 고려해야 하고, 이건 하드웨어 명령을 재전송할 때의 중복 실행 위험과 같은 문제입니다. 또한 JS에서는 타임아웃으로 "포기"한 비동기 작업이 실제로 취소되는 게 아니라 백그라운드에서 계속 실행되기 때문에, 나중에 공유 상태(ctx)를 뒤늦게 건드려서 race condition을 일으킬 수 있다는 것도 배웠습니다.

## 추가 Q&A: CLAUDE.md/AGENTS.md도 AI 오케스트레이션인가?

**질문**: "CLAUDE.md", "AGENTS.md" 같은 파일을 쓰는 것도 AI 오케스트레이션의 일부로 볼 수 있나?

- **답변**: 엄밀히는 아님. 오케스트레이션은 "런타임에 여러 단계/에이전트를 어떻게 조합·순서·분기시키는지"(오늘 만든 `Pipeline`처럼 순서 실행, 재시도, 타임아웃, 실패 시 skip/fail 결정)를 가리킴. `CLAUDE.md`/`AGENTS.md`는 에이전트가 세션 시작 시 한 번 읽는 **정적인 컨텍스트/설정**이라서, 오케스트레이션보다는 **"컨텍스트 엔지니어링"**에 더 가까움.
- **비유**: Kubernetes의 YAML 설정 파일 = 선언적 설정(이건 `CLAUDE.md` 역할), 실제로 그 설정을 읻고 파드를 띄우고 재시작·스케일링하는 **Kubernetes 자체** = 오케스트레이터(이건 오늘 만든 `Pipeline` 같은 역할).
- 멀티 에이전트 시스템에서 각 에이전트가 자기 역할을 담은 설정 파일을 읻고 동작한다면, 그 파일은 "오케스트레이션 시스템이 참조하는 설정값"일 뿐이고, 그 설정을 바탕으로 여러 에이전트를 실제로 조합·순서 제어하는 쾅이 오케스트레이션임. 면접에서 이 둘을 구분해서 말할 수 있어야 함.
