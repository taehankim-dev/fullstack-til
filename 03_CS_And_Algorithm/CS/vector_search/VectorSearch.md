# 벡터 검색 / 임베딩 기초

## 1. 문제 정의 및 실무 맥락
- 기존 검색(PostgreSQL의 `LIKE`, Full-Text Search 등)은 "단어가 정확히 일치하는지"를 찾음. 근데 "강아지"로 검색했을 때 "반려동물"이라는 단어가 쓰인 문서도 찾고 싶다면? 단어는 다른데 **의미**가 비슷한 거라서, 기존 방식으로는 못 찾음.
- 이걸 가능하게 하는 게 **임베딩(Embedding)**: 텍스트(또는 이미지 등)를 고차원 숫자 벡터로 변환하는 것. AI 모델이 "의미가 비슷한 것들은 벡터 공간에서 서로 가까운 위치에 놓이도록" 학습해둠. 즉 **"의미의 유사성"이 "벡터 사이의 거리(또는 각도)"로 바뀜.**
- 그래서 "의미 검색"은 결국 수학적으로 **"벡터 공간에서 질문(query) 벡터와 가장 가까운 벡터들을 찾는 문제"**가 됨 — 이를 최근접 이웃 탐색(Nearest Neighbor Search)이라고 함.
- 문제: 벡터가 수백만~수십억 개 쌓이면, 매 검색마다 모든 벡터와 일일이 거리를 계산하는 건 O(n)이라 실시간 서비스(예: RAG 챗봇의 "관련 문서 찾기")에는 너무 느림.
- 지난 B-Tree 세션에서 "정렬된 데이터에서 빠르게 찾기"를 다뤘는데, 벡터는 "정렬"이라는 개념이 없는 고차원 공간이라 B-Tree 방식이 그대로 안 통함. 그래서 벡터 전용의 **근사(Approximate) 탐색** 구조가 필요함 — "정확히 가장 가까운 것"이 아니라 "거의 가까운 걸 빠르게" 찾는 타협.
- 참고: 실제로 PostgreSQL의 `pgvector` 확장이 제공하는 인덱스(HNSW 등)가 바로 이 역할을 함 — 네가 쓰는 DB 스택과 직접 연결되는 지점.
- 오늘은 먼저 "임베딩 벡터 + 코사인 유사도로 가장 비슷한 벡터 찾기"를 브루트포스(O(n))로 구현해서 의미 검색의 기본 동작을 체감하고, 그다음 "왜 이게 느린지 / 어떻게 빠르게 할지(ANN)"로 이어갈 것.

## 2. 구현 요구사항
```typescript
export function cosineSimilarity(a: number[], b: number[]): number {}

export class VectorStore {
  add(id: string, vector: number[]): void {}

  // query와 가장 유사한 벡터 topK개를, 유사도 높은 순으로 반환
  search(query: number[], topK: number): Array<{ id: string; score: number }> {}
}
```

**제약조건**
- `cosineSimilarity(a, b)`: 두 벡터 사이의 코사인 유사도 = **내적(dot product) / (각 벡터의 크기(norm)를 곱한 값)**. 결과는 -1~1 사이, **1에 가까울수록 "방향이 비슷함"(유사함)**, 0이면 직각(무관), -1이면 반대 방향.
- `VectorStore.search`: 저장된 모든 벡터와 query의 코사인 유사도를 계산해서, **유사도 내림차순으로 상위 K개**를 반환 (지금은 브루트포스로 — 전부 비교해도 괜찮음, 이게 왜 문제가 되는지는 나중에 다룰 것)

**테스트 예시**
```typescript
cosineSimilarity([1, 0], [1, 0]);   // 1 (완전히 같은 방향)
cosineSimilarity([1, 0], [0, 1]);   // 0 (직각)
cosineSimilarity([1, 0], [-1, 0]);  // -1 (반대 방향)

const store = new VectorStore();
store.add("a", [1, 0]);
store.add("b", [0.9, 0.1]); // a와 비슷한 방향
store.add("c", [0, 1]);     // a와 직각

store.search([1, 0], 2);
// [{ id: "a", score: 1 }, { id: "b", score: 0.99... }] 순서로 나와야 함 (c는 제외)
```

## 3. 내가 작성한 코드
실제 구현은 [vector-search.ts](./vector-search.ts) 참고. `npm test`로 [vector-search.test.ts](./vector-search.test.ts) 포함 전체 테스트 22개 통과 확인함.

- `cosineSimilarity`: `reduce`로 내적(dot)과 두 벡터의 크기(norm)를 각각 구해서 `dot / (normA * normB)`.
- `VectorStore`: `{id, vector}[]` 배열에 저장. `search`는 전체를 `map`으로 유사도 계산 → `sort`로 내림차순 정렬 → `slice(0, topK)`.

## 4. 코드 리뷰 피드백

**정확함.**

**복잡도**: 벡터 차원을 `d`, 저장된 벡터 개수를 `n`이라 하면, 유사도 계산 전체 O(n·d) + 정렬 O(n log n) → **O(n·d + n log n)**. 1단계에서 말한 "브루트포스 O(n)"이 정확히 이 형태.

**엣지케이스 (참고, 수정 불필요)**:
- 영벡터(`[0,0]`)끼리 비교하면 norm이 0이 되어 0으로 나누기 → `NaN`
- `a`, `b`의 길이가 다르면 에러 없이 `NaN`이 조용히 섞여 들어감 (더 위험한 유형의 버그)

**가독성**: `reduce`/`map`/`sort`/`slice` 조합이 깔끔함.

## 5. 꼬리질문과 답변

### 1. 벡터 1억 개, 차원 1536일 때 검색 1회에 필요한 연산량과 실시간 서비스에 쓰기 어려운 이유?

- **답변**: 몇억 개의 연산이 필요할 것 같다. 연산만 하다가 시간을 다 보내서 사용자가 이탈할 수 있다.
- **정리**: 결과(사용자 이탈)와 원인(연산에 시간이 많이 걸림)의 방향은 정확하지만, 규모를 과소평가함. 벡터 하나당 내적 계산 ≈ 3000번 연산(곱셈+덧셈), 1억 개 벡터면 `3000 × 1억 = 3,000억(3×10^11)번` — "몇억"이 아니라 "몇천억" 단위. 핵심은 연산량이 데이터 개수에 **정확히 비례(O(n))**해서, 데이터가 늘어날수록 끝없이 느려지는 구조적 문제라는 것.

### 2. "정확한 최근접" 대신 "근사 최근접(ANN)"으로 타협하면 뭘 포기하고 뭘 얻을까?

- **답변**: 정확도를 줄이는 대신 빠른 속도를 얻는다. 어디까지 근사로 둘지 트레이드오프를 체크하는 작업이 필요하다.
- **정리**: 정확함. 실제로 pgvector의 HNSW 인덱스도 `ef_search` 같은 파라미터로 이 "정확도 vs 속도" 트레이드오프를 조절할 수 있게 해줌 — 네가 말한 "체크하는 작업"이 실무에서 실제로 하는 튜닝.

## 6. 면접용 설명 요약
> 기존 키워드 검색은 단어가 정확히 일치해야 찾을 수 있는데, "의미가 비슷한 것"을 찾으려면 임베딩이 필요합니다. 임베딩은 텍스트를 고차원 벡터로 바꿔서, 의미가 비슷한 것들이 벡터 공간에서 서로 가깝게 위치하도록 만드는 기법입니다. 그래서 의미 검색은 결국 "질문 벡터와 가장 가까운 벡터를 찾는 최근접 이웃 탐색" 문제로 바뀝니다. 저는 코사인 유사도(내적을 두 벡터 크기의 곱으로 나눈 값)를 이용해 브루트포스 방식의 벡터 검색을 직접 구현해봤습니다.
>
> 이 구현의 복잡도는 저장된 벡터 개수 n과 차원 d에 대해 O(n·d + n log n)입니다. 벡터가 1억 개, 차원이 1536(실제 임베딩 모델 차원 중 하나)이라고 가정하면 검색 한 번에 약 3000억 번의 연산이 필요한데, 이건 실시간 서비스에 쓰기엔 너무 느립니다. 이 문제를 실제 시스템(예: PostgreSQL의 pgvector가 쓰는 HNSW 인덱스)은 "근사 최근접 이웃(ANN)" 방식으로 해결하는데, 100% 정확한 최근접 대신 약간의 정확도를 포기하고 속도를 얻는 트레이드오프입니다. 이 트레이드오프의 정도는 파라미터(예: ef_search)로 조절할 수 있어서, 서비스 요구사항에 맞게 속도와 정확도의 균형을 맞추는 튜닝이 실무에서 이루어집니다.
