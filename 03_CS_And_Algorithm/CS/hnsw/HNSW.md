# ANN 탐색 - Navigable Small World 그래프 (HNSW 맛보기)
| HNSW : Hierarchical Navigable Small World

## 1. 문제 정의 및 실무 맥락
- 지난 세션에서 브루트포스 벡터 검색이 벡터 1억 개 기준으로 검색 1회에 3000억 번 연산이 필요하다는 걸 숫자로 확인했음. 데이터가 늘어날수록 **선형(O(n))**으로 느려지는 구조적 문제.
- 오늘은 PostgreSQL `pgvector`가 실제로 쓰는 HNSW(Hierarchical Navigable Small World) 인덱스의 핵심 아이디어 중 "그래프 기반 탐욕적 탐색(greedy graph search)" 부분을 직접 구현해봄. (전체 HNSW는 "계층(여러 층)"까지 포함하는 더 큰 구조인데, 오늘은 그 중 기초가 되는 **단일 층 그래프 탐색(Navigable Small World, NSW)**부터.)
- 핵심 아이디어: 모든 벡터와 비교(O(n))하는 대신, **"이웃끼리만 연결된 그래프"**를 미리 만들어두고, 그 그래프 위에서 "지금보다 더 가까운 이웃이 있으면 그쪽으로 이동"을 반복하면서 탐색함. 지난 BFS/DFS 세션에서 배운 그래프 순회가 여기서 다시 등장함 — 다만 "전부 방문"이 아니라 "더 가까운 쪽으로만 욕심내며 이동(greedy)"하는 점이 다름.
- 비유: 전화번호부를 처음부터 끝까지 넘기는 게 아니라, "이 사람이랑 친한 사람 몇 명"만 알아두고, "내가 찾는 사람과 더 비슷한 친구가 있으면 그쪽으로 물어보러 이동"을 반복하는 것. 친구의 친구를 타고 가다 보면 의외로 빨리 도달하는 "좁은 세상(Small World)" 현상을 활용하는 거라서 이름이 Navigable **Small World**.
- 트레이드오프: 이 방식은 "욕심내며 이동하다가 그 지점에서 더 가까운 이웃이 없으면 멈춰버리는" **지역 최적해(local optimum)**에 빠질 위험이 있음 — 그래서 "근사(Approximate)" 최근접이지, 100% 정확한 최근접은 보장 못 함. (진짜 HNSW는 이 문제를 "계층 구조"로 완화하는데, 그건 4단계에서 다룰 것.)

## 2. 구현 요구사항
그래프 구성(`buildGraph`)은 이미 구현해뒀어 — 각 노드를 자신과 가장 유사한 상위 k개의 다른 노드와 연결하는 것뿐이라, 지난 세션에서 한 "유사도 계산 + 정렬 + 상위 K개"를 각 노드마다 반복하는 것과 같음. 오늘 네가 구현할 건 **탐욕적 탐색(`greedySearch`)** — HNSW의 실제 검색 메커니즘의 핵심.

```typescript
interface GraphNode {
  id: string;
  vector: number[];
  neighbors: string[]; // 연결된 다른 노드들의 id
}

export class NSWGraph {
  // ... buildGraph(k)는 이미 구현되어 있음 (각 노드를 상위 k개 유사 노드와 연결)

  // entryId에서 시작해서, 현재 노드보다 query와 더 유사한 이웃이 있으면 그쪽으로 이동.
  // 더 유사한 이웃이 없으면 멈추고, 그 시점의 노드를 "근사 최근접"으로 반환.
  greedySearch(query: number[], entryId: string): { id: string; score: number } {}
}
```

**요구사항**
- `current`를 `entryId`로 시작. 매 단계마다 `current`의 이웃들 중 `query`와 가장 유사한 이웃을 찾기.
- 그 이웃의 유사도가 **현재 노드의 유사도보다 높으면** 그 이웃으로 이동 (반복).
- 더 높은 이웃이 없으면 멈추고, 현재 `{id, score}`를 반환.
- 전체 노드를 다 보는 게 아니라 **그래프를 따라서만** 이동해야 함 (브루트포스로 다시 돌아가면 안 됨).

**테스트 예시** (2차원 벡터를 각도가 다른 점들로 구성, `k=2`로 그래프 구성)
```typescript
const graph = new NSWGraph();
graph.add("A", [1, 0]);
graph.add("B", [0.95, 0.31]);
graph.add("C", [0.5, 0.87]);
graph.add("D", [0, 1]);
graph.add("E", [-1, 0]);
graph.buildGraph(2);

graph.greedySearch([0, 1], "A");
// entry가 A여도, A -> C -> D 순으로 그래프를 타고 이동해서 D(score 1)에 도달해야 함
```

## 3. 내가 작성한 코드
실제 구현은 [graph-search.ts](./graph-search.ts) 참고. `npm test`로 [graph-search.test.ts](./graph-search.test.ts) 포함 전체 테스트 25개 통과 확인함.

`current`를 entry로 시작 → 매 반복마다 이웃들 중 query와 가장 유사한 것을 찾아 → 그게 현재 점수보다 **엄격히 높을 때만** 이동 → 더 높은 이웃이 없으면 멈추고 반환.

## 4. 코드 리뷰 피드백

**정확함.** (buildGraph로 만든 샘플 그래프에서 A→C→D, E→D 모두 올바르게 진짜 최근접 D에 도달함을 테스트로 확인)

**복잡도**: 이동 1회당 O(k·d) (k=이웃 수, d=벡터 차원). 전체는 O(이동 횟수 × k × d) — 브루트포스 O(n·d)보다, "이동 횟수"가 `n`보다 훨씬 작을 때 이득을 봄.

**엣지케이스**: 이웃이 없는 노드에서 시작하면 즉시 멈추고 entry 자신을 반환 — 자연스럽게 처리됨. 무한 루프 위험 없음 — `>`(엄격한 부등호) 조건 덕분에 점수가 매번 반드시 증가해야 이동하므로 사이클 불가능, 유한 노드 안에서 반드시 종료.

## 5. 꼬리질문과 답변

### 1. "점수가 엄격히 증가해야만 이동"하는 조건이 왜 사이클도 막아줄까?

- **답변**: 점수가 동일하면 같은 노드를 반복하다가 무한 루프에 빠질 것 같아서.
- **정리**: 정확함. `>=`를 썼다면 유사도가 같은 두 노드(A↔B)가 서로를 "최선의 이웃"으로 가리키는 상황에서 A→B→A→B를 영원히 왕복할 수 있음. `>`로 막으면 이동할 때마다 점수가 반드시 이전보다 커져야 해서, 한 번 지나간 점수로는 절대 못 돌아옴 — 사이클이 구조적으로 불가능해짐.

### 2. 그래프 연결이 엉성하면 지역 최적해에 빠질 수 있는데, 진짜 HNSW의 "계층(layer)" 구조가 왜 이 문제를 완화할까?

- **답변**: 잘 모르겠음.
- **멘토 설명**: 연결(`k`)이 적으면 "가까운 이웃만 아는" 상태로 먼 곳까지 짧은 걸음을 아주 많이 거쳐야 해서, 그 경로 중간에 지역 최적해에 갇히기 쉬움. HNSW는 그래프를 여러 층으로 쌓아서 이를 완화함:
  - **맨 위층**: 노드 수가 적고 "먼 거리를 잇는 지름길(long-range edge)" 위주 — 적은 이동으로 "대략 맞는 영역"까지 빠르게 도달.
  - **아래로 내려갈수록**: 노드가 많아지고 "가까운 이웃" 위주로 촘촘해짐.
  - 탐색은 맨 위층에서 그리디 탐색 → 그 결과를 아래층의 entry point로 전달 → 다시 그리디 탐색, 이걸 맨 아래층까지 반복.
  - 핵심: **"이미 대략 맞는 근처에서 출발"하기 때문에, 촘촘한 아래층에서 길을 잃고 엉뚱한 지역 최적해에 갇힐 위험이 크게 줄어듦.**
  - 지난 B-Tree 세션의 "노드에 키를 여러 개 담아 분기 수를 늘려 높이를 낮춘다"는 것과 같은 직관 — B-Tree는 "정렬된 범위"를, HNSW는 "벡터 공간의 영역"을 좁혀간다는 차이만 있을 뿐, 둘 다 "성긴 상위 구조로 크게 좁히고 촘촘한 하위 구조로 정밀하게 마무리"하는 패턴.

## 6. 면접용 설명 요약
> 브루트포스 벡터 검색이 데이터가 늘어날수록 선형으로 느려지는 문제를 풀기 위해, PostgreSQL pgvector가 실제로 쓰는 HNSW 인덱스의 핵심 아이디어 중 "그래프 기반 탐욕적 탐색(Navigable Small World)"을 구현해봤습니다. 모든 벡터와 비교하는 대신, 각 벡터를 가장 유사한 상위 k개의 다른 벡터와 미리 연결해 그래프를 만들고, 그 그래프 위에서 "지금보다 더 유사한 이웃이 있으면 그쪽으로 이동"을 반복하는 탐욕적(greedy) 탐색으로 근사 최근접을 찾습니다.
>
> 이 방식은 이동할 때마다 점수가 반드시 이전보다 엄격히 커져야만 이동하도록 구현했는데, 이 덕분에 같은 노드를 영원히 왕복하는 사이클 없이 항상 종료된다는 걸 보장할 수 있었습니다. 복잡도는 이동 횟수 × 이웃 수 × 벡터 차원인데, 브루트포스의 O(n·d)보다 이동 횟수가 전체 데이터 개수보다 훨씬 작을 때 이득을 봅니다.
>
> 다만 이 "한 층짜리" 그래프 탐색은 연결이 엉성하면 지역 최적해에 갇혀 진짜 최근접을 놓칠 위험이 있습니다. 실제 HNSW는 이를 여러 층으로 쌓아서 완화하는데, 위층은 노드가 적고 먼 거리를 잇는 지름길 위주라 빠르게 대략적인 영역까지 도달하고, 그 결과를 다음 층의 시작점으로 넘겨가며 점점 촘촘한 층에서 정밀하게 좁혀갑니다. 이건 B-Tree가 "노드에 키를 여러 개 담아 분기 수를 늘려 높이를 낮추는" 것과 같은 직관으로, 성긴 상위 구조로 크게 좁히고 촘촘한 하위 구조로 정밀하게 마무리하는 패턴이 반복되는 것이라는 걸 배웠습니다.
